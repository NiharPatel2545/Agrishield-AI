# AgriShield

AI-powered soil intelligence from satellite imagery, climate data, and
machine learning — live pH-risk and organic-carbon estimates for any
coordinate on Earth, no lab test required.

## What it actually does

Given a single lat/lon, the API pulls live data from three sources —
Google Earth Engine (Sentinel-2 bands + NDVI), WorldClim (climate
normals), and OpenLandMap/SRTM (soil texture + elevation) — and feeds
them into two trained models:

- **Soil acidity classifier** — predicts whether soil pH is likely
  below 5.5 (acidic), with a confidence score.
- **Organic carbon regressor** *(experimental)* — estimates organic
  carbon content in g/kg.

Both are tuned XGBoost models, trained on harmonised LUCAS (EU) and
WoSIS (global) survey data, validated with a leakage-safe grouped
train/test split (no physical sampling point appears in both train
and test) and a continent-holdout check (trained with an entire
continent excluded, then tested on it) to measure real-world
generalisation rather than just in-distribution accuracy.

A response also includes a **regional confidence tier**, derived from
the actual measured continent-holdout recall for that region — not a
guessed number — so a farmer in a well-covered region and one in a
sparse-data region get an honestly different confidence signal.

Crop suggestions are matched against a filtered subset of the FAO
EcoCrop database (temperature/rainfall/pH-tolerant food crops only),
not generated by the model itself.

## What it does NOT do (yet)

- No bulk/CSV upload or enterprise dashboard backend — the "Enterprise"
  section of the website is an illustrative mockup, not connected.
- No authentication/user accounts beyond a single shared API key.
- Crop suggestions use pH tolerance only; temperature, rainfall, and
  soil-texture matching are not yet wired in (see the full EcoCrop
  database if extending this).
- No real-world field validation yet — all accuracy figures are from
  held-out survey data (LUCAS/WoSIS), not live farmer usage.

## Project layout

```
agrishield/
  config.py        # feature list, paths, target column
  dataset.py        # LUCAS + WoSIS harmonisation -> data/agrishield_training.csv
  gee.py             # Google Earth Engine queries (Sentinel-2, static soil, elevation)
  climate.py         # WorldClim + Sentinel-2 enrichment pipeline, batched + checkpointed
  model.py           # training (classifier + OC regressor), continent-holdout checks
  inference.py       # live per-coordinate feature fetch + regional confidence
  weather.py         # current-weather lookup (OpenWeather), display only, not a model input
  farmer_report.py   # turns a raw prediction into a farmer-facing summary + crop suggestions
  geography.py       # rough lat/lon -> continent lookup, used only for the confidence tier
  api.py             # FastAPI service exposing /scan
data/
  agrishield_training.csv   # built by dataset.py, enriched by climate.py
  crop_requirements.csv     # filtered EcoCrop data used by farmer_report.py
models/
  soil_risk_model.joblib    # trained classifier
  oc_model.joblib           # trained OC regressor
Agrishield.ipynb   # the actual pipeline: build -> enrich -> train -> validate
train_pipeline.py  # CLI equivalent of the notebook's build/enrich/train steps
```

## Running it locally

**1. Backend**
```
pip install -r requirements.txt
cp .env.example .env   # fill in GEE_PROJECT_ID and OPENWEATHER_API_KEY
uvicorn agrishield.api:app --reload
```
Check it's up at `http://127.0.0.1:8000/docs`.

**2. Rebuilding the training data / retraining a model**

Run `Agrishield.ipynb` top to bottom. It auto-skips the slow satellite
enrichment step if `data/agrishield_training.csv` already has those
columns filled in, so re-running it after the first full pass is fast.
`train_pipeline.py` does the same thing as a script instead of a
notebook, if you'd rather run it headless.

**3. Frontend**

A separate Vite/React project that calls this API over HTTP -- two
different services, deployed independently, not one codebase. See
that project's own setup instructions.

## Known limitations, stated plainly

- Regional accuracy is uneven: the model generalises noticeably worse
  to continents with less training data (Asia in particular). This is
  a data-coverage problem, not expected to be fixed by further tuning
  alone.
- `geography.py` is a rough bounding-box classifier for the confidence
  tier only -- not precise at continental borders (documented in the
  file itself).
- This is a prototype validated on public survey data, not yet on
  real farmer-submitted field results.
